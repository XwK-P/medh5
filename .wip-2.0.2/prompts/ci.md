## Items (quoted from the audit; verify each first)
1. **Top issue 16:** release builds use moving inputs. They build with `stable` Rust plus `clippy -D warnings`, re-run on the tag, with the newest maturin and cmake, and with `curl | sh` rustup in the container (`.github/workflows/ci.yml:38,68,303`; `release.yml:237`; `.github/scripts/build-dist.sh:18-30`).
   - Pin the Rust toolchain in `rust-toolchain.toml`, bumped on purpose, with the `rustfmt` and `clippy` components.
     - This environment has rustc/cargo 1.97.0; check with `rustup show` whether rustup is present, and pin a version that exists here so local builds don't break.
     - Make every CI job and `build-dist.sh` use the pinned toolchain. With dtolnay/rust-toolchain, use the toolchain file or pass the same version.
   - Pin maturin and cmake in `build-dist.sh`; optionally pin the manylinux image digests.
2. **Advisory gates** (both audits agree):
   - Add a scheduled and release-time `cargo audit` or `cargo deny` over `Cargo.lock`, and `pip-audit` over the extras.
   - Keep a native inventory (HDF5 2.2.0, zlib 1.3.2, C-Blosc2 3.3.5, LZ4 1.10.0, Zstd 1.5.7) with a reasoned disposition per advisory, because RustSec cannot see vendored C.
   - The first entry is CVE-2026-85091:
     - it is a heap overflow in zlib's `gz_vacate`, and zlib 1.3.1.2–1.3.2 is affected, so the bundled 1.3.2 is in range;
     - it is **not reachable**: `nm` on the built `_core` shows no `gz*` symbol, only `compress2`/`uncompress`/`deflate`/`inflate`;
     - scanners keyed on the version will still flag the wheels, so record a VEX "not affected" statement, and bump `libz-sys` once a fixed zlib ships.
   - Verify the symbol claim yourself on `/home/user/medh5/medh5/_core.abi3.so` (`nm -D` or `nm`). The sources: osv.dev/vulnerability/CVE-2026-85091, the Debian and Ubuntu trackers.
   - `dependabot.yml` covers GitHub Actions only. Consider adding the `cargo` and `pip` ecosystems, grouped and weekly; decide and report.
3. **CI efficiency:**
   - add `Swatinem/rust-cache` to the non-release jobs, SHA-pinned like the other actions;
   - add `timeout-minutes` to every job;
   - add `fail-fast: false` to the Python matrix;
   - give artifacts a short retention for PRs.
4. **Python 3.15:** add it to the test matrix, with `allow-prereleases` until it is available. The classifier comes only once it is green, so don't add it now.
5. **Backports:** a backport (e.g. 2.0.x after 2.1.0) would become GitHub "Latest" and downgrade the Homebrew tap. Compare the tag with the highest release, and pass `--latest=false` and skip the tap when it is not the newest (`.github/scripts/release.py:322-326`; `release.yml:323-336`).

   - `pre-commit-hooks` is pinned to 2024; bump it to a current release (check the version actually exists).
7. **W6:** add `strip = "symbols"` to `[profile.release]`; about 5 MB of symbols sit in the 30 MB extension. Check that it doesn't conflict with anything in `release.yml` or `build-dist.sh`, such as separate debug-symbol uploads.

Add both to CLAUDE.md and CONTRIBUTING.md, keeping the two consistent; CONTRIBUTING is the human-facing version. Never write `---` as a dash in CONTRIBUTING.md; write `—`.
9. **Extras floors:** test the declared floors (`torch>=2.0`, `monai>=1.3`, `nibabel>=5`, `pydicom>=3.0`, `highdicom>=0.23`), or raise them to what CI tests. Prefer a CI job that installs the floors (`pip install "torch==2.0.*"`… where wheels exist for that Python version) over changing the published metadata. If the floors cannot be tested on any supported Python, report it; don't edit dependency floors.
10. **W9:**
    - Read engine output with an older HDF5 (1.10–1.14) in CI. The spec promises "HDF5 ≥ 1.10", but the engine links HDF5 2.2.0 with `libver_bounds(V110, latest)`, and the test suite's h5py 3.16 bundles HDF5 2.0.0. Add a CI job that writes files with the engine (e.g. the conformance corpus) and reads them with an h5py whose wheels bundle HDF5 1.12 or 1.14. Find the right h5py version from h5py's release notes. Alternatively report that an upper-bound cap is needed.
    - Speed: `tests/project/test_packaging.py:217` takes a large share of the run. Make it cheaper without losing what it checks.
    - Wall-clock bounds in Rust unit tests run on unoptimised Windows and macOS runners. Find them (grep `elapsed`, `Instant` in `crates/**/src` tests) and make them robust, e.g. generous bounds or `#[cfg_attr(debug_assertions, ignore)]`, with a comment. Those are localized edits in Rust files you don't own: keep them minimal, and list them.
